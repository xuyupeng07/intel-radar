## 1. 背景与问题

### 1.1 真实的一天

情报工作者的日常并不是「找不到信息」，而是四件事同时发生：

1. **源太散**：门户、公众号、券商研报、交易所公告、政策网站、招投标、社媒、海外媒体，各在一处。
2. **重复太多**：一条消息被 20 家媒体转载，人工要读 20 遍才知道是同一件事。
3. **判断太慢**：读完了才想起来「这条和我们有什么关系」，相关性判断发生在阅读之后，而不是之前。
4. **分发靠手**：整理好的内容要复制到群里，格式还经常被 IM 吃坏（表格、加粗、链接）。

### 1.2 现有方案为什么不够

| 方案 | 能解决 | 卡在哪 |
|---|---|---|
| 人工检索 + 浏览器收藏 | 灵活 | 不可持续，无法覆盖长尾；人一休假就断更 |
| RSS 阅读器（Inoreader / Feedly 免费版） | 订阅与聚合 | 只做「送到你面前」，不做去重、不打分、不生成日报；中文源覆盖差 |
| 舆情 SaaS（识微 / 鹰眼 / 慧科等） | 全网监测、预警、报告 | 贵、按项目报价；偏「声誉/危机」，不贴行业研究与投研工作流；数据难导出、难二次加工 |
| 通用 AI 搜索（Perplexity / 秘塔 / 元宝） | 单次问答快 | 每次都要重新提问；不沉淀；不主动推送；不能按团队主题长期跟踪 |
| 自建脚本（爬虫 + GPT + 机器人） | 便宜、可控 | 一次性的；没有去重、没有溯源、没有重试、没有成本控制，两周后就开始报错 |
| 自动化平台（n8n / Dify / Coze） | 编排能力强 | 需要自己搭数据模型与去重逻辑；日报质量取决于提示词，缺少自动发布与版本 |

**机会**：把「多源搜索编排 + AI 归并 + 自动日报 + IM 分发」做成一个开箱即用的系统，让一个人 10 分钟配好，第二天早上就有日报。

### 1.3 我们赌的三个判断

- **搜索 API 会越来越便宜、越来越多**（DeepSeek 官方搜索已按次计费、秘塔/博查按次），所以「统一编排层」比「自建爬虫」更有长期价值。
- **AI 生成的内容必须可追溯**，但不加人工审批：出错靠修订版与回滚兜底，而不是靠每天有人守着。
- **分发渠道决定使用率**，日报必须出现在用户已经在的地方（企微/钉钉/飞书群），而不是要求用户再打开一个网站。

## 2. 产品定位

### 2.1 一句话

> 给团队用的、可自建的行业情报雷达：每天把该看的行业信息筛出来、去重、说清楚「发生了什么、为什么重要、出处在哪」，并在你上班前送到群里。

### 2.2 是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 主题驱动的**持续监测**系统 | 一次性问答的 AI 搜索 |
| 有出处、可追溯的**情报简报** | 无来源的 AI 摘要生成器 |
| 可插拔搜索服务的**编排层** | 又一个爬虫框架 |
| 面向团队的**分发 + 反馈**工作流 | 个人 RSS 阅读器 |
| 轻量、可私有化部署 | 替代 Bloomberg / Wind 的金融终端 |

### 2.3 差异化（相对 §竞品调研 的三条）

1. **Provider 抽象**：同一主题可同时挂博查 + 秘塔 + DeepSeek + Tavily，按能力路由、按成本降级、按结果去重合并。
2. **零审批**：`生成 → 发布 → 可修订`，没有人工审核环节；读者只看到结果，采集量与成本只在管理员看板出现。
3. **IM 原生**：统一中间表示（Brief AST）渲染成企微 markdown、钉钉 markdown、飞书卡片、邮件 HTML，而不是把一份 Markdown 到处贴。

## 3. 用户与角色

| 角色 | 目标 | 关键动作 | 权限 |
|---|---|---|---|

## 4. 目标与成功指标

### 4.1 业务目标

| 时间 | 目标 |
|---|---|
| 上线 2 周 | 3 个主题稳定出报，连续 7 天无人工干预失败 |
| 上线 1 个月 | 日报平均打开率 ≥ 60%；读者「有用」反馈率 ≥ 70% |
| 上线 3 个月 | 覆盖 10+ 主题、5+ 信息源类型；单份日报综合成本 ≤ 3 元 |

### 4.2 指标树

**北极星：每周被「读完并点击至少一条来源」的日报份数**（衡量真实使用，不是推送量）

| 层 | 指标 | 口径 |
|---|---|---|
| 采集 | 源覆盖率 / 抓取成功率 / 时效 | 成功任务占比；事件发布 → 入库 P50 ≤ 30 分钟（搜索源）、P95 ≤ 2 小时 |
| 质量 | 去重率 / 相关性准确率 / 事实错误率 | 重复条占比；抽检 50 条中「与该主题相关」的比例 ≥ 85%；抽检事实错误 ≤ 2% |
| 生产 | 日报生成成功率 / 修订率 / 生成时长 | 成功率 ≥ 99%；修订率 ≤ 5%（发布后需要出修订版的期数占比）；单份 ≤ 3 分钟 |
| 分发 | 到达率 / 打开率 / 点击率 | 渠道 API 返回成功为准；打开率 ≥ 60%；点击率 ≥ 25% |
| 成本 | 单份日报成本 / 单条情报成本 | 搜索费 + 模型费 + 存储，按日记账 |
| 体验 | 首次配置到出第一份日报的时间 | 目标 ≤ 15 分钟 |

### 4.3 首版「算成功」的验收口径

- 新建一个主题 → 次日 08:30 自动产出日报 → 同时到达站内与企业微信群；
- 日报中任意一条都能点回原始链接，且能看到发布时间与抓取时间；
- 人为关掉一个 Provider，系统自动降级到备用源并在运行日志中留痕；
- 人为让推送失败，系统重试 3 次后告警，不重复刷屏。

## 5. 核心场景

### S1 · 早间金融日报（主场景）

- **触发**：每日 08:30（可配时区与时间）
- **流程**：前一晚 20:00 起增量采集 → 02:00 批量聚类与打分 → 07:30 生成 → 08:30 自动推送企微/钉钉/飞书/邮件，全程无人工
- **成功标准**：8 分钟内读完；Top3 命中当天真正的行业大事；每条有出处。

### S2 · 盘中突发预警

- **触发**：预警规则命中（如「某公司 + 减持/立案/停产」「某原材料 + 涨价 ≥ 10%」）
- **流程**：实时采集（5–15 分钟级）→ 规则匹配 → 去重 → 生成 3 行短讯 → 立即推送并 @ 值班人
- **成功标准**：比人工发现早 ≥ 30 分钟；不重复告警（同一事件 6 小时内只推一次）。

### S3 · 周一竞品/行业周报

- **触发**：每周一 09:00
- **流程**：聚合过去 7 天已入库情报 → 按公司/事件聚类 → 生成「本周 5 件事 + 趋势判断 + 下周三件待观察」
- **成功标准**：能直接贴进管理层周会材料；可导出 Markdown/PDF。

### S4 · 临时专题深挖

- **触发**：用户手动发起「专题：固态电池量产进展」
- **流程**：多 Provider 并发检索（不限时间窗）→ 深度抓取正文 → 聚类成 5–8 条主线 → 输出带引用的专题报告
- **成功标准**：10 分钟内拿到可用的初稿，引用链接 ≥ 15 条。

## 6. 功能需求

> 优先级：**P0** = 首版必须；**P1** = 第二版；**P2** = 后续。
> 每条需求都写「规则与边界」，因为这类系统 80% 的坑在边界。

### FR-01 信息源与搜索服务接入（P0）

**目标**：任何「能返回信息」的服务，都能在 30 分钟内接进来，且对上层无感。

**需求点**

1. 统一的 `SearchProvider` 能力契约（不是统一参数，而是**能力声明 + 适配**）：

```ts
interface SearchProvider {
  id: string;                    // bocha | metaso | deepseek | tavily | searxng ...
  capabilities: {
    web: boolean;
    news: boolean;               // 新闻垂直
    academic: boolean;
    siteFilter: boolean;
    dateFilter: boolean;
    langFilter: boolean;
    content: boolean;            // 是否直接返回正文
    summary: boolean;
    maxResults: number;
  };
  search(req: SearchRequest): Promise<SearchResult[]>;
  healthCheck(): Promise<HealthStatus>;
}
```

2. **内置适配器清单**（v1 至少 4 个，v1.5 补齐）：

| Provider | 类型 | 可用的关键能力 | 计费口径 | 适配注意 |
|---|---|---|---|---|
| 博查 Bocha | 中文网页/AI 搜索 | 摘要、时效与站点过滤 | 按次（开放平台） | 中文源覆盖好，注意 `summary/content` 字段差异 |
| 秘塔 Metaso | 中文 AI 搜索 | 多模态、深度搜索、来源列表 | 约 0.03 元/次起 | 返回偏「答案 + 引用」，需拆出引用 |
| DeepSeek Search / Fetch | 官方搜索 + 抓取 | `site:` `after:` `lang:` 操作符、`rerank_score`、`authority`、`site_name`/`site_icon`、正文 Markdown | $0.75 / 1000 次成功请求 | 自带权威度、时间与站点图标，直接用于排序与来源头像；QPS 100 / 25 |
| Tavily | 面向 LLM 的搜索 | answer、raw content、topic/days | 按 credit | 英文源强，正文可直接入库 |
| Serper / SerpAPI | Google SERP | 新闻垂直、结果全 | 按次，成本较高 | 作为兜底，不作为主力 |
| Exa | 语义搜索 | 相似站点、语义近邻 | 按次 | 用于「找同类报道 / 同类公司」 |
| SearXNG | 自建元搜索 | 免费、可聚合多引擎 | 自建 | 稳定性与反爬自担，仅作兜底 |
| RSSHub | RSS 生成 | 财联社、华尔街见闻、36 氪等 | 自建 | 站点改版即失效，必须有健康检查 |
| 官方 API / RSS | 结构化源 | 交易所公告、巨潮、政策库、招投标 | 免费或授权 | **最稳定，优先级最高** |
| 通用网页抓取 | 兜底 | 任意站点正文 | 自建 | 合规与反爬风险最高，默认关闭 |

3. **多源并发与合并**：同一主题下多 Provider 并行检索 → URL 归一化去重 → 标题/正文相似度去重 → 按「相关性 × 权威性 × 新鲜度」融合排序。
4. **密钥管理**：加密存储（AES-GCM，密钥来自环境变量）、界面只显示后四位、支持一键连通性测试。
5. **配额与降级**：每个 Provider 可设日/月配额；超额或连续失败自动切备用链；失败率 > 30% 触发告警。
6. **成本可见**：每次调用记录 provider / 查询 / 条数 / 计费单位 / 估算金额。

**规则与边界**

- 不做「一个万能参数」的假统一：能力不支持的请求必须显式降级（如 Provider 不支持日期过滤，则由本地时间窗二次过滤）。
- 同一 query 在 24 小时内命中缓存则直接复用，避免重复计费。
- Provider 返回的正文长度做截断（默认 20k 字符）后再进模型。

**验收**：新增一个 Provider 只需实现适配器 + 注册，不改上层逻辑；关闭主 Provider 后任务仍能出报。

### FR-02 主题、关键词与采集调度（P0）

**目标**：用户用「主题」表达关注点，系统把它翻译成一组定时查询。

**需求点**

1. **主题**：名称、描述、行业标签、关注实体（公司/产品/人物/机构）、排除词、时间窗、语言。
2. **查询规则**：每个主题可挂多条 query，支持模板变量 `{entity}`、`{industry}`、`{date}`；可指定 Provider 子集与条数。
3. **调度**：按主题配置频率（实时 15 分钟 / 每小时 / 每日 / 每周）与运行时间窗；支持 Cron 表达式。
4. **增量水位**：记录每个 query 的最后成功时间与已见 URL 指纹，只取新增。
5. **手动触发**：立即运行、补跑某天、单条 query 调试（返回原始结果，便于调提示词）。
6. **健康度**：每个源显示近 7 天「命中数 / 失败数 / 平均延迟」，长期 0 命中的 query 提示优化。

**规则与边界**

- 单个主题单日调用预算上限（默认 50 次），超出需管理员放行。
- 关键词变更后不回溯历史，除非用户显式点「补采近 N 天」。
- 同一 query 并发去重：同一时刻只跑一个实例（分布式锁）。

**验收**：新建主题 10 分钟内可手动跑出结果；调度失败有日志与告警。

### FR-03 正文抓取与解析（P0）

**目标**：拿到「可被模型读、可被人核对」的正文。

**需求点**

1. 抓取策略优先级：Provider 自带正文 → 官方 API → 静态抓取（Readability）→ 无头浏览器渲染（仅白名单站点）。
2. 解析产物：标题、作者、发布时间、正文 Markdown、主图、站点名、canonical URL。
3. **原文快照**：正文落对象存储（MinIO），保留 90 天，支持「快照对比」。
4. 失败处理：超时 15s、重试 2 次、失败入库为 `fetch_failed` 并进入人工可重试队列。
5. 去广告与导航：保留正文与图表说明，去掉推荐位。

**规则与边界**

- 遵守 robots.txt 与站点条款；命中 403/429 立即退避，不换 IP 硬闯。
- 付费墙内容不绕过，只保留标题与摘要，并标注「需订阅」。
- 单站点并发 ≤ 2，全局并发可配。

**验收**：给定 20 个常见财经站点 URL，正文抽取成功率 ≥ 90%。

### FR-04 去重、聚类与实体（P0）

**目标**：把「20 家媒体转载同一件事」压成「1 条情报 + 20 个来源」。

**需求点**

1. **指纹去重**：URL canonical 化 → 标题 simhash → 正文 shingle；阈值可配。
2. **语义聚类**：embedding 相似度 + 时间窗（默认 72 小时）+ 实体重合度，聚成 `event_cluster`。
3. **实体抽取**：公司、产品、人物、机构、金额、时间、地点、事件类型（融资/并购/政策/财报/人事/诉讼/停产/涨价…）。
4. **代表条选择**：每个 cluster 选一条「主稿」（权威性 × 完整度 × 时效），其余作为「其他来源」。
5. **合并展示**：日报中一条情报下列出 2–5 个来源，标注首发媒体与首发时间。

**规则与边界**

- 聚类宁松勿紧：错聚类（把两件事合成一件）比漏聚类更伤信任。
- 同一事件跨天持续发酵时，允许「事件续报」关联到同一 cluster，但在日报中标注「第 N 天」。
- 实体词典支持用户自定义别名（如「宁德时代 / CATL / 宁王」）。

**验收**：人工标注 100 条样本，聚类 F1 ≥ 0.8；重复条进入日报的比例 ≤ 3%。

### FR-05 AI 整合与可信度（P0）

**目标**：不是「总结文章」，而是「回答这条情报对读者意味着什么」。

**需求点**

1. **分段处理**（控制成本与质量）：
   - 粗筛：便宜模型对每条打「相关性 0–100 + 一句话理由」→ 淘汰 70%；
   - 精读：对入选条抽取「事实 / 数据 / 观点 / 引语」；
   - 整合：对同一 cluster 做多源交叉，生成「发生了什么 / 关键数字 / 为什么重要 / 与我何干」；
   - 编排：按模板组装日报，写导语与板块小结。
2. **事实与观点分离**：事实句必须能对应到来源；观点句标注「据 XX 分析」。
3. **交叉验证标记**：≥ 2 个独立来源一致 → 「已多源印证」；仅 1 个来源 → 「单一来源，待确认」。
4. **结构化输出**：一律 JSON Schema 约束（标题、要点、影响、来源 ID、置信度），解析失败自动重试 1 次后降级为「仅标题 + 来源」。
5. **提示词与模型版本化**：提示词存库、可灰度；每次生成记录 model / prompt_version / token / 成本。
6. **反馈闭环**：读者的「有用 / 不够」与偶尔的抽检结论，进入周度评测集，用于调提示词与阈值。

**规则与边界**

- **禁止无源断言**：模型输出中任何带数字的句子，必须绑定 `source_id`，否则整条降级。
- 数字不跨源合并（A 说 10 亿、B 说 12 亿 → 并列呈现，不取平均）。
- 涉政、涉个人隐私、未证实传闻 → 默认不进日报，只在预警中提示。
- 单条情报的模型调用成本上限可配（默认 0.05 元）。

**验收**：抽检 100 条，事实错误率 ≤ 2%；每条均有 ≥ 1 个可点击来源。

### FR-06 日报 / 周报生成（P0）

**目标**：把覆盖窗口内的全部情报，整合成一篇有主线、有洞察、可溯源的稿子，而不是把情报逐条列出来。

**需求点**

1. **覆盖窗口**：金融日报默认覆盖前一个自然日（08:00 — 次日 08:00），周报覆盖最近 7 天；覆盖区间写在正文开头。
2. **整合稿结构**：
   - **导语**：1 段，三句话内说清「发生了几件事、主线是什么」；
   - **正文**：3–5 个主题小节，每节 1–2 段自然语言，跨来源归纳因果、对比与影响，**不逐条罗列**；
   - **情报洞察**：3 条可执行的结论，放在全文最后，整段标注为模型观点；
   - **来源**：正文用 `[n]` 数字标签，hover 预览来源卡、点击回原文；底部「来源自 N 个网页」pill 打开搜索结果面板。
3. **写作约束**：一段只讲一件事；数字必须带单位与口径；多源冲突时并列呈现，不取平均；不写「综上所述」这类空话。
4. **长度**：日报 600–1200 字，周报 1200–2000 字；超出说明素材过多，应提高入选阈值。
5. **版本**：每次生成新 revision，保留 diff；发布后只能发修订版并标注变更。
6. **导出**：Markdown、HTML、PDF、长图（P1）。
7. **正文格式**：AI 直接产出 Markdown（`##` 标题、段落、`-` 列表），主题小节用 `1.` / `2.` 编号，导语、情报洞察、来源不编号；目录从 `##` 标题提取。

**规则与边界**

- 日报是「覆盖窗口的快照」：补跑历史日期时，只使用该时点之前发布的内容（防穿越）。
- 每条事实必须有来源；情报洞察段落允许无来源，但必须整段标注「模型观点」。
- 生成失败不推空日报，改推「本期生成失败，稍后重试」。

**验收**：连续 14 天自动出报；抽检 10 期，正文中「逐条罗列」的比例为 0；每个 `[n]` 都能在来源里找到对应条目；修订率 ≤ 5%。

### FR-07 自动发布与修订（P0）

**目标**：日报生成即发布，全流程没有人工审批环节。

**需求点**

1. **发布策略**：生成完成后按模板的发布时间自动推送（默认 08:30），支持「生成即推」与「定时推送」。
2. **修订**：发布后发现错误，可重新生成 v2 并推送「修订版」，原文保留供回看。
3. **版本记录**：每期保留 revision、生成模型、来源清单与推送回执；不记录「谁审核了」。
4. **读者反馈**：有用 / 一般 / 不够好，进入周度选题评测，不阻塞发布。
5. **例外处理**：生成失败不推空日报，推「本期生成失败，稍后重试」，并进入运行记录。

**规则与边界**

- 没有「待审核 / 已通过」状态；状态只有 `生成中 → 已发布 → 已修订 / 生成失败`。
- 修订版必须在标题区标注「修订：新增 N 条，更正 M 条」。
- 管理员只能「撤回」一期（错误严重时），撤回不影响已读用户。

**验收**：连续 30 天无需人工操作即可发布；修订版可追溯到 diff。

### FR-08 多渠道分发（P0）

**目标**：一份日报，五种到达方式，格式都不坏。

**需求点**

1. **渠道清单**：

| 渠道 | 接入方式 | 消息形态 | 关键约束（实现时以官方文档为准） |
|---|---|---|---|
| 站内 | 自带 | 富文本 + 目录 + 收藏 | 无 |
| 邮件 | SMTP | HTML（内联样式） | 需处理图片外链与暗色模式 |
| 企业微信 | 群机器人 Webhook（可选加签） | markdown / text | 长度有限（约 4096 字节），markdown 支持子集；有频率限制 |
| 钉钉 | 自定义机器人 Webhook（加签 + 关键词/IP 白名单） | markdown / link / actionCard | 需配置安全设置；有频率限制 |
| 飞书 | 自定义机器人 Webhook（可选签名校验） | text / post / interactive 卡片 | 卡片需构建 JSON；有频率限制 |
| 通用 Webhook | 自定义 HTTP | JSON（Brief AST） | 供自建系统/自动化平台消费 |
| Slack / Teams | Webhook | Block Kit / Adaptive Card | P1 |

2. **渲染适配层**：内部统一 `BriefDocument`（块级 AST）→ 各渠道 renderer。必须处理：标题层级降级、表格降级为列表、长文截断 + 「阅读全文」链接、链接卡片化。
3. **推送策略**：按渠道分组（群/人）、按时区、按发送窗口；支持「测试发送」到指定群。
4. **幂等**：`delivery_key = brief_id + channel_id + revision`，唯一索引，重试不重复。
5. **重试与告警**：失败按 10s / 1min / 5min 退避重试 3 次 → 死信 → 告警（站内 + 管理员 IM）。
6. **回执与统计**：记录 HTTP 状态、响应码、耗时；打开/点击用带 UTM 的短链统计（P1）。

**规则与边界**

- 渠道密钥同样加密存储，界面上只显示后四位。
- 单个渠道连续失败 3 次自动暂停并提示，不影响其他渠道。
- 内容长度超限时优先保留「今日必读 + 链接」，不整段截断。

**验收**：同一份日报在企微/钉钉/飞书三端排版可读，无乱码、无裸 Markdown 符号；重复点击「立即推送」不产生重复消息。

> 见 [backend-sqlite.md](backend-sqlite.md)。下表是完整产品目标模型；`provider`、`channel`、
> `delivery`、`usage_record`、`feedback` 等属于后续能力，当前版本没有建表，也没有对应页面。

| 表 | 作用 | 关键字段 |
|---|---|---|

| `event_cluster` | 事件簇 | title, first_seen, last_seen, entities[], sources_count, score |
| `brief` | 日报 | date, template_id, status, revision, model, cost |
| `brief_item` | 日报条目 | brief_id, cluster_id, section, rank, headline, body, source_ids[] |

## 9. 关键流程与规则

### 9.1 日报状态机

```text
generating ──成功──> published ──修订──> revised ──> archived
     │                    │
     └──失败──> failed     └──撤回──> archived
```

- 没有审批态：生成成功即发布，`published` 是读者可见的唯一常态。
- 每次「重新生成」生成新 revision，不覆盖已发布版本，并在标题区标注修订说明。
- 推送失败不回滚状态：内容已发布，失败只记在 delivery 与看板上。

### 9.2 分发幂等与重试

1. 生成 `idempotency_key = sha1(brief_id + channel_id + revision)`，入库唯一约束。
2. 发送前查 key：已成功 → 直接返回「已发送」；失败 → 允许重试。
3. 重试 3 次（10s/1min/5min）后写死信，告警一次（同一 key 24h 内只告警一次）。

### 9.3 降级策略

| 故障 | 降级 |
|---|---|
| 主 Provider 失败 | 切备用 Provider；全失败则用最近 24h 缓存结果并标注「时效可能滞后」 |
| 模型超时/限流 | 降级到备用模型；再失败则只出「标题 + 来源」清单版日报 |
| 正文抓取失败 | 用 Provider 摘要；标注「仅摘要」 |
| 渠道失败 | 单渠道隔离，其余照发；站内始终可读 |
| 数据库不可用 | 任务进入队列等待，不丢任务 |

### 9.4 成本控制

- 三级预算：单次任务 / 单日 / 单月，超限即停并告警。
- 缓存优先：同 query 24h、同 URL 正文 7 天。
- 模型分级：粗筛用便宜模型（占比 ~80% 调用），整合用强模型。
- 去重前置：先去重再调模型，避免为转载内容重复付费。

## 10. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 单主题日采集 ≤ 5 分钟；日报生成 ≤ 3 分钟；站内首屏 LCP ≤ 2.5s |
| 可靠性 | 日任务成功率 ≥ 99%；推送失败可重试且不重复；数据不丢（任务持久化） |
| 安全 | 密钥 AES-GCM 加密、日志脱敏、RBAC、审计日志、Webhook 出站签名可选 |
| 合规 | 遵守 robots 与站点条款；不绕过付费墙；转载只存摘要 + 链接；个信数据脱敏 |
| 可观测 | 结构化日志、任务 trace、Provider 健康度、成本台账 |
| 可维护 | Provider/渠道/模板均为配置驱动，新增不改核心代码 |
| 部署 | Docker Compose 一键起（Web + Worker + PG + Redis + MinIO）；支持私有化 |

### 成本估算（示例，非承诺）

假设 20 个主题、每主题每日 5 条 query、挂 2 个 Provider：

| 项 | 量 | 单价 | 日成本 |
|---|---|---|---|
| 搜索调用 | 20 × 5 × 2 = 200 次 | 混合（DeepSeek ≈ ¥0.005/次，秘塔 ≈ ¥0.03/次） | ≈ ¥3.5 |
| 正文抓取 | 约 200 次 | ≈ ¥0.005/次 | ≈ ¥1 |
| 粗筛模型 | 约 600 条 | 便宜模型 | ≈ ¥1–2 |
| 整合模型 | 约 30 簇 × 3 次 | 强模型 | ≈ ¥3–6 |
| **合计** | | | **≈ ¥9–13 / 天，约 ¥300–400 / 月** |

> 实际取决于条数与模型选择；首版必须在成本看板里可验证。

## 11. 合规与风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 抓取公众号/小红书/抖音等封闭平台 | 封号、法律风险 | **不直接抓**，走第三方合规数据源或官方 API；默认关闭该类源 |
| 转载全文 | 版权风险 | 只存快照用于内部核对，对外只发摘要 + 链接 |
| AI 幻觉与错误数字 | 决策误导、信任崩塌 | 强制溯源、数字不跨源合并、每周抽检、修订版与一键撤回 |
| 模型供应商数据条款 | 敏感情报外泄 | 提供「公有云 / 私有化模型」切换；敏感主题强制本地模型 |
| 推送内容外发 | 群机器人发到外部群 | 渠道绑定群 ID 白名单；发布前二次确认 |
| 个人隐私 | 个信保护法风险 | 人名/联系方式脱敏；不做个人画像 |
| 供应商限流/涨价 | 成本与稳定性 | 多 Provider 冗余 + 配额告警 + 成本台账 |

## 12. 里程碑

| 阶段 | 周期 | 范围 | 验收 |
|---|---|---|---|
| **M0 打通闭环** | 1 周 | Provider 抽象 + 博查/DeepSeek 两个适配器；单主题采集；日报生成（无审核）；站内 + 企微推送 | 手动跑通一次「采集 → 日报 → 企微」 |
| **M1 可用** | 2–3 周 | 主题/查询管理、调度、去重聚类、自动发布与回执、钉钉/飞书/邮件、运营看板 | 连续 7 天自动出报，三端排版正常 |
| **M2 好用** | 4–6 周 | 实体与聚类优化、周报/专题、站内检索与实体主页、预警规则、反馈闭环 | 抽检事实错误 ≤ 2%，修订率 ≤ 5% |
| **M3 扩展** | 6 周+ | 竞品官网变更监控、招投标/政策/专利/融资垂直源、OpenAPI 与 MCP、多租户 | 新增源 ≤ 1 天接入 |

> 里程碑按「一条链路端到端可用」切，不按前后端切。

## 13. 明确不做（v1）

1. 不做移动端 App / 小程序。
2. 不做面向外部客户的营销站点与在线支付。
3. 不做 Bloomberg/Wind 级别的行情与财务数据库。
4. 不做封闭平台（公众号、小红书、抖音）的直连爬虫。
5. 不做人工审批流，也不做多人实时协同编辑。
6. 不做知识图谱可视化大屏。
7. 不做自动对外发布到公开社媒账号。
